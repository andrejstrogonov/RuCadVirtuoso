## 1. Назначение и область

Документ фиксирует проверяемые требования к двум блокам MVP:

1. **Хранение проекта** — каталог `<project>.rcad/`, версионирование формата, содержимое схем ячеек, кэш скомпилированных моделей.
2. **Пользовательский интерфейс** — редактор схем, иерархия и символы, ERC-lite, Netlist-вью, диалоги запуска анализа и импорта Verilog-A, просмотрщик результатов, панель логов, горячие клавиши, персистентность и восстановление, внешний вид и поведение при больших схемах.
3. **Сквозные приёмочные сценарии S1–S4** (п. 3 ТЗ) как E2E-требования уровня UI-API.

Каждое требование имеет уникальный идентификатор, приоритет, критерий проверки (измеримое условие приёмки) и метод тестирования ISTQB. Трассировка на пункты ТЗ и тест-кейсы — в разделе 6.

**Термины.** *Cell* — ячейка схемы (файл `cells/<cell>.json`); *instance* — экземпляр мастера на схеме; *master* — мастер-ячейка или модель/примитив, на который ссылается instance; *SV* — state variable прибора; *net* — электрический узел; *UI-API* — программный интерфейс приложения, позволяющий выполнить пользовательский сценарий без ручного ввода (п. 12.1 ТЗ, уровень «UI smoke»).

**Допущения, зафиксированные из ТЗ.**
- Отображение координат схемы — пиксели логического холста (сетка 10 px, п. 10.1).
- Cache проекта содержит только производные артефакты (DLL и метаданные) и не является источником истины.
- Опциональные по ТЗ элементы (символы `symbols/`, UI-автоматизация) получают приоритет Should/Could и не блокируют приёмку.

## 2. Модель качества и методы проверки

Классификация требований: **FR** — функциональные (поведение при заданных входах), **NFR** — нефункциональные (качество, совместимость, устойчивость, юзабилити, тестируемость). Для UI обе категории формулируются как наблюдаемое поведение, чтобы исключить субъективные формулировки.

| Метод ISTQB | Применение в этом документе | Код в трассировке |
|---|---|---|
| Boundary value analysis | Сетка, undo/redo (граница 50), 500 инстансов, 30 fps, 5 минут автосохранения, размер каталога | BVA |
| Equivalence partitioning | Валидные/невалидные значения параметров, корректные/повреждённые JSON, поддерживаемые/неподдерживаемые `.va` | EP |
| Decision table | Валидация панели свойств, ERC-lite (4 класса ошибок), поведение Import VA (нет MSVC / ошибка трансляции / успех) | DT |
| State transition | Жизненный цикл документа (чистый/изменён/автосохранён/восстановлен после падения) | ST |
| Use case testing | Сквозные сценарии S1–S4 | UC |
| Experience-based (checklist) | Отзывчивость UI, отсутствие «нервных» перерисовок, читаемость сообщений | CH |

**Правило формулировки критерия.** Критерий приёмки должен быть проверяем без интерпретации: число, порог, перечень или структурное утверждение. Если ТЗ задаёт только качественную формулировку («автоматическое присвоение имён»), критерий уточняется до наблюдаемого инварианта, не добавляя новых пользовательских функций.

## 3. Функциональные требования

### 3.1 Формат проекта и хранение (ТЗ 6.1)

| ID | Требование | Приоритет | Критерий приёмки | Метод |
|---|---|---|---|---|
| FR-PRJ-001 | Проект хранится как каталог `<project>.rcad/`; сохранение создаёт каталог с расширением `.rcad`, открытие — принимает такой каталог. | Must | После «Сохранить как» в файловой системе существует каталог `<name>.rcad`; открытие этого каталога возвращает проект с тем же именем и тем же набором ячеек. | ST, EP |
| FR-PRJ-002 | Каталог проекта содержит `project.json`, `cells/`, `symbols/`, `models/`, `veriloga/`, `cache/` в соответствии с п. 6.1 ТЗ; отсутствующие необязательные подкаталоги создаются при первой записи. | Must | Для проекта с 1 ячейкой без символов и моделей после сохранения присутствуют `project.json` и `cells/`; `symbols/` и `models/` создаются только при появлении соответствующих сущностей; `cache/` создаётся при первой компиляции VA. | EP |
| FR-PRJ-003 | `project.json` содержит имя проекта, версию формата и перечень используемых библиотек. | Must | JSON валиден, содержит поля имени, версии формата (целое число) и списка библиотек; имя проекта в `project.json` совпадает с именем каталога без расширения `.rcad`. | EP |
| FR-PRJ-004 | Версионирование формата: при открытии проект с версией формата выше поддерживаемой приложение отказывает в открытии с сообщением и не изменяет файлы проекта. | Must | Открытие проекта с версией формата `MAX+1` даёт ошибку с указанием версий; хэши всех файлов проекта до и после попытки открытия совпадают. | EP, DT |
| FR-PRJ-005 | Проект с версией формата ниже поддерживаемой открывается с предупреждением; запись выполняется только в текущей версии формата после явного подтверждения пользователя. | Should | При открытии старого проекта в панели логов появляется warning; без подтверждения файлы не перезаписываются; после подтверждения `project.json` содержит текущую версию формата. | ST |
| FR-PRJ-006 | Схемы хранятся по одной на ячейку: `cells/<cell>.json`; имя файла соответствует имени ячейки. | Must | Создание ячеек `A`, `B` даёт ровно файлы `cells/A.json`, `cells/B.json`; переименование ячейки переименовывает файл. | EP |
| FR-PRJ-007 | Каталог `cache/` содержит только производные артефакты (скомпилированные DLL и метаданные) и исключается из VCS-контроля; при отсутствии `cache/` проект открывается и функционирует, кэш пересоздаётся. | Must | Удаление `cache/` и повторное открытие проекта не дают ошибок; симуляция воспроизводится (при наличии MSVC — после перекомпиляции); в репозитории примеров `cache/` отсутствует (проверка по `.gitignore`/`.git`). | EP, ST |
| FR-PRJ-008 | Исходники моделей `.va` хранятся в `veriloga/` в виде исходных файлов, без преобразования исходного текста. | Must | После импорта `my_rram.va` файл `veriloga/my_rram.va` побайтно совпадает с импортированным. | EP |
| FR-PRJ-009 | Параметры встроенных моделей (`.model`) хранятся в `models/<name>.json`; изменение параметров в панели свойств приводит к записи в соответствующий файл модели. | Must | Изменение `Vp` мемристора и сохранение проекта даёт в `models/<name>.json` новое значение `Vp`; повторное открытие показывает изменённое значение. | ST |
| FR-PRJ-010 | Символьные представления хранятся в `symbols/<cell>.json` опционально; при отсутствии файла символ генерируется автоматически (п. 6.1, 10.1 ТЗ). | Should | Проект без `symbols/` открывается, все ячейки отображаются на холсте; при явной настройке символа файл `symbols/<cell>.json` создаётся и повторно используется после переоткрытия. | EP, ST |
| FR-PRJ-011 | Проект, сохранённый на одной машине, открывается и воспроизводит результаты на другой машине (п. 2 ТЗ, п. 4): сохранение не содержит абсолютных путей машины-источника. | Must | Поиск абсолютных путей в `project.json`, `cells/*.json`, `models/*.json` даёт 0 совпадений; проект, перенесённый в другой каталог (и другая учётная запись), открывается и запускает анализ без ручного исправления путей. | EP, UC |
| FR-PRJ-012 | Повреждённый JSON-файл ячейки не приводит к потере всего проекта: открытие сообщает файл и ошибку разбора, остальные ячейки доступны. | Must | Подмена `cells/<cell>.json` на невалидный JSON даёт error с именем файла в панели логов; остальные ячейки открываются; приложение не падает. | EP |

### 3.2 Содержимое схемы ячейки (ТЗ 6.1)

| ID | Требование | Приоритет | Критерий приёмки | Метод |
|---|---|---|---|---|
| FR-CEL-001 | `cells/<cell>.json` содержит список инстансов; каждый инстанс — имя, мастер-ячейка и параметры. | Must | Для схемы из 3 инстансов в JSON присутствуют 3 записи с непустыми именем и мастером; переоткрытие восстанавливает имена и параметры один-в-один. | EP |
| FR-CEL-002 | Для каждого инстанса сохраняются координаты на холсте. | Must | Перемещение инстанса и сохранение меняет координаты в JSON; переоткрытие показывает тот же пиксельный сдвиг (в пределах 1 px). | ST, BVA |
| FR-CEL-003 | Для каждого инстанса сохраняются поворот (0/90/180/270) и зеркало (по X/Y), в том числе при комбинации поворота и зеркала. | Must | 8 комбинаций (4 поворота × 2 зеркала) сохраняются и восстанавливаются без потери и без перестановки флагов. | BVA, ST |
| FR-CEL-004 | Для ячейки сохраняется список соединений: net-имена и привязки выводов инстансов/портов к net. | Must | Схема «2 резистора, 3 net, 1 земля» после сохранения и переоткрытия даёт идентичный netlist по сравнению экспорта (текстовое сравнение через UI-API export). | EP |
| FR-CEL-005 | Для ячейки сохраняется список портов ячейки; порты отличаются от внутренних net типом привязки. | Must | Создание порта `IN`, сохранение и переоткрытие: `IN` присутствует в списке портов и отсутствует среди внутренних net. | EP |
| FR-CEL-006 | Для ячейки сохраняются её свойства (атрибуты уровня ячейки). | Could | Добавление пользовательского свойства ячейки, сохранение и переоткрытие — свойство присутствует с прежним значением. | EP |
| FR-CEL-007 | Запись схемы атомарна: прерывание записи (аварийное завершение процесса во время save) не оставляет частично записанный `cells/<cell>.json`. | Should | При принудительном завершении процесса во время save файл ячейки либо содержит предыдущую валидную версию, либо новый валидный JSON; файл, не разбираемый как JSON, не наблюдается. | ST |

### 3.4 Соединения и net-имена (ТЗ 10.1)

| ID | Требование | Приоритет | Критерий приёмки | Метод |
|---|---|---|---|---|
| FR-WIR-001 | Инструмент «провод» соединяет два вывода инстанса (или порта) и создаёт net. | Must | Протяжка провода от вывода A к выводу B создаёт один net, привязанный ровно к двум выводам; промежуточные клики по холсту не создают «висячих» net. | EP |
| FR-WIR-002 | Нет-имена присваиваются автоматически в виде `n1`, `n2`, … без повторного использования номера в пределах ячейки до явного переименования. | Must | Создание 5 последовательных net даёт `n1`…`n5`; удаление `n3` и создание нового net не приводит к двум net с одинаковым именем в одной ячейке. | BVA, EP |
| FR-WIR-003 | Узел земли `0` доступен без автонумерации: соединяемые выводы могут быть привязаны к net `0`. | Must | Привязка вывода к земле даёт в экспорте netlist номер узла `0`; автоимя `nK` для земли не создаётся. | EP |
| FR-WIR-004 | Ручное переименование net валидируется: недопустимые символы отклоняются, совпадение с существующим net отклоняется либо требует объединения (явное решение пользователя). | Must | Имена с пробелами/недопустимыми символами отклоняются с сообщением; ввод существующего `n2` даёт диалог выбора «отклонить/объединить», молчаливой перезаписи не происходит. | DT, EP |
| FR-WIR-005 | Провод, соединяющий выводы при отключённой привязке, тем не менее регистрирует электрическое соединение только при фактическом совпадении координат вывода. | Should | Провод, «недоведённый» до вывода на 1 px, не создаёт соединения и подсвечивается как незавершённый; после привязки соединение создаётся. | BVA |

### 3.6 Выделение, undo/redo (ТЗ 10.1)

| ID | Требование | Приоритет | Критерий приёмки | Метод |
|---|---|---|---|---|
| FR-SEL-001 | Выделение одним кликом и рамкой (marquee) для инстансов и проводов. | Must | Клик выделяет ровно один объект; рамка, полностью покрывающая N объектов, выделяет N; частично покрытый объект не выделяется (или выделяется согласно документированному правилу — единообразно). | EP |
| FR-SEL-002 | Групповые операции (перемещение, поворот, зеркало, удаление, копирование) применяются ко всему выделению. | Must | Перемещение рамкой 3 инстансов и 2 проводов сохраняет взаимное расположение (относительные координаты неизменны). | EP, BVA |

## 7. Критерии готовности блока и открытые вопросы

**Блок UI/хранения готов к приёмке, если:**
1. Все требования приоритета **Must** имеют статус «пройдено» с приложением отчёта прогона UI-01…UI-25 и S1–S4.
2. Требования **Should** либо пройдены, либо перенесены с решением заказчика и записью в отчёте приёмки.
3. Требования **Could** реализуются только если не ставят под риск сроки этапов E3–E4 (п. 15.1 ТЗ).
4. Достигнуты целевые показатели NFR-PERF-UI-001…004 и NFR-ROB-001.

**Открытые вопросы, влияющие на этот блок** (из п. 17 ТЗ и уточнений формата):
- Уточнить, считается ли объединение net при переименовании обязательной функцией MVP (влияет на FR-WIR-004, сейчас — явное решение пользователя).
- Уточнить состав свойств ячейки (`cells/<cell>.json`) — перечень атрибутов уровня ячейки в ТЗ не детализирован (FR-CEL-006, приоритет Could).
- Уточнить требование к формату экспорта netlist (кодировка/переносы строк) для воспроизводимости на другой машине (FR-NLV-003, FR-PRJ-011).
